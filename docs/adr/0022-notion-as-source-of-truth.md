# ADR-0022: 글의 정본은 노션에 두고, 동기화로 읽기 소스를 채운다

- 상태: 수락됨
- 날짜: 2026-09-04

## 맥락 (Context)

지금은 글을 직접 만든 에디터로 쓴다. Milkdown을 붙이고([ADR-0015](0015-editor-milkdown.md)), 에디터와 읽기 쪽 마크다운을 맞추고([ADR-0018](0018-editor-reader-markdown-compat.md)), 이미지 크기 선택 UI를 만들고([ADR-0019](0019-image-size-picker.md)), 안 쓰는 이미지를 쓸어내는([ADR-0020](0020-unused-image-sweep.md)) 작업이 차례로 필요했다.

ADR-0018이 존재한다는 사실 자체가 이 방식의 성격을 보여준다. **에디터를 직접 소유하면 쓰는 쪽과 읽는 쪽을 계속 맞춰야 하고, 그 일은 끝나지 않는다.** 표준이 바뀌거나 기능을 하나 늘릴 때마다 양쪽을 손봐야 한다.

한편 이 블로그는 글쓴이가 한 명이고, 아직 발행된 글이 없다. 지금이 정본을 옮길 수 있는 마지막 시점에 가깝다.

## 결정 (Decision)

**글의 정본(source of truth)을 노션 데이터베이스로 옮긴다.** 앱은 글을 쓰는 곳이 아니라 읽는 곳이 된다.

읽기 경로는 지금 구조를 유지한다. 노션을 화면에서 직접 조회하지 않고, **동기화 단계가 노션을 읽어 Supabase `posts`를 채운다.**

```
노션(정본) --[동기화]--> Supabase posts --[queries.ts]--> 화면
                    \
                     └--> R2 (이미지 실물, ADR-0023)
```

- **동기화는 단방향이다.** 노션이 항상 이긴다. 앱에서 글을 수정하지 않으므로 충돌이 존재하지 않는다.
- **본문은 노션 공식 마크다운 API(`GET /v1/pages/:page_id/markdown`)로 받는다.** 블록 변환기를 직접 만들지 않는다. `posts.content`가 이미 마크다운 문자열이라 그대로 저장하면 되고, 화면은 기존 마크다운 렌더러([ADR-0014](0014-markdown-content.md))를 그대로 쓴다.
- **본문 안의 이미지는 동기화 때 R2로 옮기고 URL을 치환한다**([ADR-0023](0023-images-on-r2.md)).
- **슬러그는 노션 속성으로 명시한다.** 제목에서 자동 생성하지 않는다 — 제목을 고쳐도 URL이 깨지지 않아야 한다.
- **노션 페이지 ID를 안정 키로 저장한다(`notion_page_id`).** 리액션·불 지피기가 글을 참조하므로, 재동기화 때 글 row가 새로 생기면 반응이 고아가 된다. upsert 기준은 이 키다.
- **동기화 트리거는 보호된 라우트 핸들러(수동)를 주로 쓰고, 하루 1회 cron을 보조로 둔다.** Vercel Hobby는 하루보다 잦은 cron을 허용하지 않는다. 발행 직후 반영은 수동 트리거로 한다.
- **직접 쓰기 경로(에디터·관리자 작성 화면)는 제거한다.** ADR-0015·0018·0019는 이 ADR로 대체된다.

`posts` 스키마([ADR-0011](0011-content-schema.md))는 `notion_page_id` 한 칸을 더하는 것 외에 유지한다. 읽기 경계(`queries.ts`)는 바뀌지 않는다.

## 이유 (Rationale)

- **에디터를 소유하지 않는다.** 유지보수 대상에서 에디터·이미지 UI·마크다운 호환 문제가 통째로 빠진다. 대신 노션 API 하나를 상대한다.
- **읽기 경계가 그대로 남는다.** [ADR-0005](0005-content-model.md)에서 "소스가 바뀌면 `queries.ts` 내부만 교체한다"고 정해뒀다. 화면·리액션·저널 캘린더는 이 변경을 모른다.
- **렌더 시점에 외부 의존이 없다.** 노션을 화면에서 직접 읽으면 노션 장애와 API 한도가 곧 사이트 장애가 된다. 동기화로 끊어두면 노션이 죽어도 블로그는 서비스된다.
- **변환기를 만들지 않는다.** 노션이 공식 마크다운 API를 제공하고, 우리 `posts.content`는 이미 마크다운이다. 두 규격이 맞아떨어져 중간 계층이 필요 없다.
- **역할이 깨끗하게 갈린다.** 노션은 내가 쓴 것, Supabase는 방문자가 남긴 것(리액션, 불 지피기).
- 쓰기 환경이 좋아진다. 모바일 작성, 초안, 표·임베드를 직접 만들지 않아도 된다.

## 고려한 대안 (Alternatives)

- **지금처럼 자체 에디터 유지** — 잘 돌아가고 있지만, 유지 비용이 계속 발생한다. 혼자 쓰는 블로그에서 에디터를 직접 만들 이유가 약하다.
- **노션을 화면에서 직접 조회(동기화 없이 ISR로만)** — 단계가 하나 줄지만, 렌더가 노션에 묶인다. 이미지도 렌더 시점에 처리할 수 없어(RSC에서 업로드 부수효과) 어차피 별도 단계가 필요하다.
- **마크다운 파일을 레포에 커밋(MDX)** — 의존이 가장 적지만, 글 쓸 때마다 커밋·배포가 필요하고 모바일 작성이 사실상 막힌다.
- **노션 블록을 마크다운 거치지 않고 바로 렌더** — 경도 블로그가 쓴 방식. 여기서는 마크다운 렌더러가 이미 완성돼 있어 굳이 새 렌더러를 만들 이유가 없다.

## 결과 (Consequences)

**좋아지는 것**
- 유지보수 대상 축소: 에디터, 이미지 업로드 UI, 에디터-리더 호환
- 글쓰기 환경 개선(모바일·초안·붙여넣기)
- 렌더 경로가 외부 서비스와 분리됨

**감수하는 것**
- 노션 API에 종속된다. 다만 정본을 마크다운으로 변환해 DB에 두므로, 노션을 떠나도 내용은 남는다.
- 발행이 즉시가 아니라 **동기화 이후**다. 체크박스를 켠 뒤 한 단계가 더 있다.
- 노션 속성(체크박스·태그·날짜)을 스키마처럼 다뤄야 한다. 속성 이름이 바뀌면 동기화가 깨진다.

**후속 작업**
1. 노션 데이터베이스 속성 설계(제목, 슬러그, type, 발행, 날짜, 태그, featured)
2. `posts.notion_page_id` 컬럼 추가
3. 동기화 라우트 핸들러 + 보호(수동 트리거, 하루 1회 cron 보조)
4. 이미지 파이프라인([ADR-0023](0023-images-on-r2.md))
5. 검증 후 Milkdown·작성 화면 제거
