# ADR-0044: 검색으로 발견되게 하는 최소 표시

- 상태: 채택
- 날짜: 2026-09-05
- 관련: ADR-0028(공유 이미지), ADR-0043(공유 카드 날짜), 이슈 #48

## 배경

서버에서 렌더하니 글 내용은 HTML 에 있다. 그런데 크롤러에게 **어디에 무엇이 있는지 알려 주는 것**이
하나도 없었다 — 사이트맵도, robots.txt 도, 구조화 데이터도, canonical 도.
개인 블로그에서 글이 검색에 안 잡히면 쓰는 이유의 절반이 사라진다.

## 먼저 고친 것 — 시각이 거짓말을 하고 있었다

사이트맵의 `lastmod` 와 구조화 데이터의 `datePublished`·`dateModified` 는 DB 의 시각을 쓴다.
그래서 붙이기 전에 그 값이 맞는지부터 봤는데, 둘 다 틀려 있었다.

- **`published_at` 이 동기화마다 `now()` 로 덮이고 있었다.** 발행일이 동기화할 때마다 앞으로 밀린다
- **동기화가 모든 글을 매번 덮어써서** `updated_at` 트리거가 전부 돌았다.
  "모든 글이 방금 수정됐다"가 된다

그대로 두고 표시만 붙였으면 **크롤러에게 매번 거짓말하는 사이트맵**이 됐을 것이다.
반복되는 거짓 신호는 사이트맵 자체의 신뢰를 깎는다.

그래서 동기화를 고쳤다.

- 반영 전에 기존 행을 읽어 **내용이 같으면 아예 쓰지 않는다**
- 이미 발행된 글은 **처음 찍힌 `published_at` 을 지킨다**

`synced_at` 은 안 바뀐 글에서 갱신되지 않는다. 읽는 곳이 없는 참고용 값이고,
그것 하나를 위해 `updated_at` 을 망치는 것이 더 큰 손해다.
마이그레이션은 필요 없었다 — 쓰기 전에 읽어 비교하는 것으로 끝난다.

## 결정

### 주소는 한 곳에서만 정한다

`src/lib/site.ts` 의 `SITE`. 예전에는 `layout.tsx` 안에만 있었는데,
이제 사이트맵·robots·구조화 데이터·RSS 가 전부 같은 주소를 알아야 한다.
네 곳이 각자 기본값을 들고 있으면 배포 도메인이 바뀔 때 한 곳이 반드시 남는다.

### 색인의 기본

- **`sitemap.ts`** — 고정 화면 셋 + 발행된 글 전부. 초안은 목록 조회가 이미 걸러낸다.
  사이트맵에만 조건을 따로 쓰면 두 곳이 언젠가 어긋난다.
  `priority` 는 쓰지 않는다 — 검색엔진이 오래전부터 무시하는 값이라
  적어 두면 "무언가 조정하고 있다"는 착각만 남는다
- **`robots.ts`** — 막을 것이 없다. 관리자 화면은 노션 전환 때 없앴고 API 는 동기화 하나뿐이다.
  그래도 `/api` 는 뺀다. 이 파일의 진짜 일은 사이트맵 위치를 알리는 것이다
- **canonical** — 홈·목록·소개·글 상세. 쿼리스트링이 붙은 주소가 중복으로 잡히지 않게

### 글을 글로 읽히게

- **`BlogPosting` JSON-LD** — 화면의 HTML 만으로는 제목이 제목인 줄은 알아도
  언제 쓴 누구의 글인지는 추측에 맡기게 된다
- **홈에 `Blog` 하나** — `Person` 을 따로 두지 않고 `Blog` 의 author 로 묶는다.
  블록을 둘로 나누면 검색엔진이 둘의 관계를 다시 추측해야 한다
- `openGraph` 에 `publishedTime`·`modifiedTime`·`authors`·`url`

`<script type="application/ld+json">` 은 이 저장소에서 `dangerouslySetInnerHTML` 을 쓰는
유일한 자리다. 값은 우리가 만든 객체뿐이고 `JSON.stringify` 를 거치지만,
`<` 는 한 번 더 막는다 — 제목에 `</script>` 가 들어오면 블록이 거기서 끊긴다.

### RSS

`/rss.xml`. 확장자가 붙어 있어야 사람이 주소만 보고 무엇인지 안다.
본문이 아니라 요약만 싣는다 — 마크다운 원문을 그대로 흘리면 리더마다 다르게 깨지고,
HTML 로 바꿔 넣으려면 렌더 경로를 하나 더 만들어야 한다.

## 검사로 지킨다

사이트맵과 피드는 **사람이 잘 열어 보지 않는 파일**이라 깨져도 한참 모른다.
그래서 만드는 일을 `src/lib/seo/feed.ts` 의 순수 함수로 빼고 `pnpm check:seo` 가 픽스처로 돌린다.
DB 도 네트워크도 필요 없다.

그 파일에는 **import 가 하나도 없다.** `@/` 별칭은 Next 빌드가 푸는 것이라 node 가 읽지 못한다.
사이트 정보와 주소 만드는 법을 인자로 받게 했더니 설계도 나아졌다 —
이 함수는 "글 목록을 XML 로 바꾼다"만 하고, 우리 사이트가 무엇인지는 부르는 쪽이 안다.

검사를 쓰다가 검사 자체가 틀린 것도 하나 잡았다. "이스케이프 결과에 `&` 가 없다"로 적었는데
`&quot;` 의 첫 글자가 `&` 다. "모든 `&` 가 엔티티의 시작이다"로 고쳤다.

빌드 뒤 세 경로를 실제로 받아 열어 확인했다.

## 남는 것

**`NEXT_PUBLIC_SITE_URL` 이 실제 배포 도메인과 같아야 한다.** 기본값은 `frost-log.vercel.app` 이다.
다르면 canonical·OG 절대경로·사이트맵·RSS 의 주소가 **전부** 어긋난다.
커스텀 도메인을 붙이면 이 값부터 바꾼다.

## 하지 않은 것

- **`keywords` 메타** — 검색엔진이 오래전에 무시한다
- **AMP·별도 정적 출력** — 지금 렌더 방식으로 충분하다
