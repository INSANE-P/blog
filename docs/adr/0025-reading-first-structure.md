# ADR-0025: 화면을 읽기 중심으로 다시 짠다

- 상태: 제안됨
- 날짜: 2026-09-05

## 맥락 (Context)

지금 화면은 기능이 먼저 생기고 목적이 나중에 붙은 상태다. 기록(`/journal`)과 이야기(`/posts`)가 갈려 있고, 저널 캘린더([ADR-0009](0009-journal-calendar.md))와 홈 큐레이션 핀([ADR-0007](0007-home-curation.md))이 있고, 이력서(`/resume`)까지 있다.

한편 [ADR-0022](0022-notion-as-source-of-truth.md)로 글의 종류 구분과 핀을 없앴다. 그 결정이 화면에 아직 반영되지 않았다.

이 블로그가 실제로 하는 일을 한 줄로 적으면 이렇다.

> 개발하면서 배운 것과 판단한 것을 쌓아두는 곳. 읽는 사람은 대개 검색으로 들어와, 한 편 읽고, 괜찮으면 누가 썼는지 본다.

필요한 것은 셋뿐이다 — **글이 잘 읽히는 것, 글을 찾을 수 있는 것, 누구인지 알 수 있는 것.**

## 결정 (Decision)

### 경로

| 경로 | 내용 |
| --- | --- |
| `/` | 짧은 소개 + **최근 6편** + 전체 보기 링크 |
| `/posts` | 전체 목록 (연도별 그룹) |
| `/posts/[slug]` | 글 + 진행률 + 목차(조건부) + 다음 글 + 불 지피기 + 댓글 |
| `/about` | 소개 + 포트폴리오·GitHub로 나가는 문 |

**없앤다**: `/journal`(글 흐름 통합), `/resume`(`resume.chanbin.dev` 로 링크만), 저널 캘린더

**미룬다**: 태그 페이지(`/tags/[tag]`). 글이 적을 때는 태그마다 1~2편이라 얇은 페이지만 늘어난다. 글에 표시만 하고 20편이 넘으면 만든다.

### 홈을 목록과 합치지 않는다

처음에는 홈 자체를 무한 목록으로 만들려 했다. 글이 적을 때 홈과 목록이 따로 있으면 둘 다 휑해 보인다는 이유였다. 하지만 그 논리는 **초기에만 유효하다.** 글이 30편을 넘기면 홈이 끝없는 목록이 되어 "이 사람이 누구인지"가 사라진다.

그래서 홈에는 **최근 6편만** 두고 전체 목록으로 가는 문을 연다. 초기에는 홈 하나로 충분해 보이고, 글이 쌓이면 자연스럽게 확장된다.

### 읽기 장치

| 장치 | 규칙 | 이유 |
| --- | --- | --- |
| 목록 썸네일 | **항상 표시** | 시각 단서가 스캔 속도를 높인다. 커버는 노션 페이지 커버 → 본문 첫 이미지 → 제목 활자 순으로 확보하므로 빌 일이 없다 |
| 읽기 진행률 | 상단 얇은 바 | 긴 글에서 남은 양을 알면 이탈이 준다 |
| 목차 | **h2가 4개 이상일 때만** | 짧은 글에 항상 띄우면 방해가 된다 |
| 코드 복사 버튼 | 코드 블록마다 | 개발 블로그에서 가장 자주 하는 동작이다 |
| 다음 글 | 본문 끝 | **다 읽은 직후가 가장 결정적인 순간이다.** 여기서 아무것도 없으면 그냥 떠난다 |

**하지 않는 것**: 읽는 중에 뜨는 구독 팝업, 공유 버튼 벽, 사이드바(통계·인기글). 절제된 타이포와 정면으로 충돌한다.

### 배치를 정할 때 쓴 기준

감으로 정하지 않기 위해 토스가 공개한 UX 원칙과 널리 쓰이는 UX 법칙을 기준으로 삼았다. 다만 **토스는 과업을 수행하는 금융 앱이고 이곳은 읽는 사이트라**, 원칙을 그대로 옮기지 않고 읽기 맥락으로 번역했다.

| 원칙 | 원래 의미 | 이 블로그에서의 적용 |
| --- | --- | --- |
| **One Thing per One Page** | 한 화면에 메시지 하나 | 글 상세에는 글만 둔다. 사이드바·추천 위젯·광고를 넣지 않는다 |
| **Minimum Features** | 목표에 꼭 필요한 기능만 | 태그 페이지·핀·시리즈를 지금 만들지 않는다. 기능 추가는 최후의 선택지 |
| **Value First, Cost Later** | 가치를 먼저, 요구는 나중에 | 구독 요청을 읽기 전에 띄우지 않는다. 다 읽은 뒤에만 다음 글을 권한다 |
| **No Ads Patterns** | 광고 문법 대신 기능으로 | 팝업·플로팅 배너를 쓰지 않는다 |
| **힉의 법칙** | 선택지가 많으면 인지 부하가 는다 | 내비게이션을 글·소개 둘로 줄인다. 홈에 6편만 노출한다 |
| **밀러의 법칙** | 작업 기억은 7±2개 | 홈의 최근 글을 **6편**으로 정한 근거. 연도별 그룹도 같은 이유 |
| **피크엔드의 법칙** | 절정과 마지막이 경험을 좌우한다 | **본문 끝**에 가장 공들인다 — 다음 글, 불 지피기, 댓글 순서 |
| **폰 레스토프 효과** | 다른 것만 기억된다 | 악센트 색을 하나만, 아껴 쓴다. 모든 곳을 강조하면 아무것도 강조되지 않는다 |
| **도허티 임계** | 0.4초 안에 반응해야 한다 | 이미지를 발행 시점에 미리 구워 두고(ADR-0023), 본문 렌더에 외부 호출을 두지 않는다 |
| **피츠의 법칙** | 터치 대상은 크고 멀지 않게 | 모바일에서 링크·버튼 터치 영역을 최소 44px로 잡는다 |

**가져오지 않은 것**: 토스의 캐주얼한 일러스트와 로딩 애니메이션. 금융의 딱딱함을 누그러뜨리려는 장치인데, 읽기 사이트에서는 본문을 방해한다. 같은 이유로 "심미적 사용성 효과"는 장식이 아니라 **타이포그래피의 완성도**로 달성한다.

## 이유 (Rationale)

- **글의 종류를 나누면 쓸 때마다 분류를 결정해야 한다.** 노션으로 옮긴 이유(마찰 제거)와 같은 논리로, 하나의 흐름이 맞다.
- **발행된 글이 0편인 지금이 URL 구조를 바꿀 수 있는 마지막 시점이다.** 나중에는 링크와 검색 색인이 얽힌다.
- **되돌리기 쉬운 것은 미룬다.** 태그 페이지·핀·목차는 나중에 추가해도 비용이 낮다. 반대로 URL 구조와 콘텐츠 모델은 되돌리기 어려우므로 지금 보수적으로 정한다.
- **`/resume`는 중복이다.** `resume.chanbin.dev` 가 이미 있고 인쇄용 PDF까지 갖췄다. 같은 내용을 두 벌 유지할 이유가 없다.

## 고려한 대안 (Alternatives)

- **홈 = 전체 목록** — 초기에는 밀도가 있지만 글이 쌓이면 소개가 사라진다.
- **기록/이야기 유지** — 저널 캘린더의 날짜 감각은 매력적이지만, 글이 갈려 양쪽 다 빈약해 보이고 매번 분류를 결정해야 한다. 태그 `기록`으로 대부분 대체된다.
- **태그 페이지를 지금 만든다** — 글 1편에 태그가 2개면 태그 페이지도 1편짜리다. 검색엔진에도 얇은 페이지로 보인다.
- **회사 기술블로그 패턴(캐러셀·시리즈·인기글)** — 토스 기술블로그 등에서 쓰지만, 저자가 여럿이고 글이 수백 편일 때 성립한다. 0편에서 시작하는 개인 블로그에 넣으면 빈 껍데기다.

## 결과 (Consequences)

**좋아지는 것**
- 쓸 때 분류를 고민하지 않는다
- 목록이 갈리지 않아 밀도가 생긴다
- 유지할 화면이 줄어든다

**감수하는 것**
- 저널 캘린더를 버린다
- 태그를 붙여도 당장은 눌러서 볼 곳이 없다
- 글이 쌓이기 전까지 `/posts`는 홈과 내용이 거의 같다
