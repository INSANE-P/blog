# ADR-0048: 캐시는 버린 뒤 데워 둔다

- 상태: 채택
- 날짜: 2026-09-05
- 관련: ADR-0045(공개 읽기 캐시), ADR-0022(노션 동기화)

## 배경

발행 체크를 켜고 동기화했는데 화면에 새 글이 안 보인다는 제보가 있었다.
확인해 보니 데이터는 전부 맞았다.

```
노션 속성   발행: true
DB          status: published
/posts      href="/posts/block-test" 있음
사이트맵     있음
RSS         있음
```

그런데 캐시 머리글이 이랬다.

```
/  →  X-Vercel-Cache: STALE
```

## 원인 — 버리는 것과 다시 만드는 것은 다른 일이다

`revalidatePath` 는 캐시를 **"낡음"으로 표시만** 한다. 다시 만드는 일은 **다음 요청**이 한다.
그리고 그 다음 요청은 옛것을 받으면서 뒤에서 재생성을 시작한다(stale-while-revalidate).

```
동기화        → 낡음 표시
첫 방문자     → 옛 화면 + 뒤에서 재생성 시작
둘째 방문자   → 새 화면
```

**글을 쓰고 동기화한 뒤 바로 확인하는 사람은 늘 그 "첫 방문자"다.**
그래서 "발행했는데 안 보인다"로 느껴진다. 새로고침하면 나오지만, 그때는 이미
무언가 잘못됐다고 생각한 뒤다.

이건 고장이 아니라 ISR 의 설계다. 방문자를 기다리게 하지 않으려고 그렇게 되어 있다.
문제는 **발행 직후의 첫 사람이 방문자가 아니라 글쓴이**라는 점이다.

## 결정

동기화가 캐시를 버린 뒤, 그 경로들을 **스스로 한 번 불러 둔다.**
재생성이 방문자의 요청이 아니라 동기화 요청 안에서 끝난다.

```
전:   동기화 → 낡음 표시 → (방문자가 옛것 받으며 재생성)
후:   동기화 → 낡음 표시 → 스스로 호출해 재생성 → (방문자는 처음부터 새것)
```

버리는 경로와 데우는 경로를 **한 배열로 묶었다.** 둘이 따로 적혀 있으면 언젠가 어긋난다 —
글 하나를 버리고 데우지 않거나, 그 반대가 된다.

**실패해도 그냥 둔다.** `Promise.allSettled` 로 받고 결과를 보지 않는다.
데우지 못하면 예전처럼 첫 방문자가 재생성을 시작할 뿐, 잘못된 화면이 나가지는 않는다.
동기화 자체를 실패로 만들 일이 아니다.

## 대가

동기화가 경로 수만큼 느려진다. 글이 스무 개면 스물네 번의 요청이 붙는다.
동기화는 사람이 눌러서 도는 일이고 상한이 300초라 여유가 있다.
그리고 그 시간은 어차피 누군가는 치러야 하는 시간이다 — 글쓴이가 치르느냐,
아무것도 모르고 들어온 첫 독자가 치르느냐의 차이일 뿐이다.

지워진 글의 경로도 데운다. 404 가 되는 것이 맞는 새 상태이므로 그대로 둔다.
