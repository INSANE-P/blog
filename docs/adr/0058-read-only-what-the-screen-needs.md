# ADR-0058: 화면이 쓰는 것만 읽는다

- 상태: 채택
- 날짜: 2026-09-06
- 관련: ADR-0045(캐시 가능한 읽기), ADR-0025(목록 썸네일), ADR-0022(노션 동기화)

## 배경

읽기 경계가 어디서나 같은 컬럼을 가져오고 있었다.

```ts
const SELECT = "slug, title, excerpt, content, cover_image, entry_date, …";
```

`content` 는 본문 마크다운이다. 한 편에 한글 5,000자면 약 15 KB.

그리고 앞뒤 글 링크가 이렇게 만들어지고 있었다.

```ts
export async function getAdjacent(slug) {
  const list = await getList();   // 전체 글을 본문째로
```

**글 하나를 열 때마다 모든 글의 본문을 읽는다.** 링크 두 개를 만들자고.
목록·사이트맵·RSS 도 같은 조회를 쓴다.

전송량이 글 수의 **제곱**으로 늘어난다. 한 편 15 KB 로 잡고 재생성이 한 바퀴 돌 때:

| 글 수 | 한 바퀴  | 시간당 전부 재생성 시 월 전송 |
| ----- | -------- | ----------------------------- |
| 10편  | 약 2 MB  | 약 1.4 GB                     |
| 30편  | 약 15 MB | 약 10.7 GB                    |
| 50편  | 약 40 MB | 약 28.6 GB                    |

Supabase 무료 요금제의 전송 한도는 월 5 GB 다.
방문이 없으면 재생성도 없으니 실제 수치는 이보다 낮다. 표는 상한이지 예측이 아니다.
그래도 **모양이 제곱이면 언젠가 넘는다** — 넘고 나서 고치면 그때는 이미 쓴 뒤다.

## 왜 본문을 가져오고 있었나

목록 썸네일이 "노션 커버가 없으면 **본문 첫 그림**"이었다(ADR-0025).
읽는 쪽에서 본문을 뒤져야 했으니 본문을 가져올 수밖에 없었다.

편의 하나가 조회 전체의 모양을 정하고 있었던 셈이다.

## 결정

**읽어 올 컬럼을 세 갈래로 나눈다.**

|        | 쓰는 곳                    | 본문 |
| ------ | -------------------------- | ---- |
| `FULL` | 글 상세 — 한 행만          | 있음 |
| `CARD` | 목록·홈·사이트맵·RSS       | 없음 |
| `NAV`  | 앞뒤 글 — 슬러그·제목·날짜 | 없음 |

**대표 이미지는 동기화가 미리 정한다.** 커버가 없으면 그때 본문에서 첫 그림을 찾아
`cover_image` 에 넣어 둔다. 이 시점의 본문은 이미 R2 주소로 바뀌어 있다 —
이미지 이관이 먼저 돌기 때문이다.

읽기는 한 번이 아니라 계속 일어나고, 쓰기는 발행할 때 한 번이다.
**같은 계산이라면 한 번 하는 쪽에서 한다.**

## 안 읽어 온 본문은 빈 문자열이 아니다

`toEntry` 가 `body` 를 `""` 로 채우고 있었다. 그러면 "본문을 안 읽었다"와
"본문이 빈 글"이 구분되지 않는다. `undefined` 로 둔다 — 타입이 이미 `body?: string` 이다.

## 대가

**옛 글의 썸네일이 한 번은 비어 보일 수 있다.** `cover_image` 는 다음 동기화에서 채워지므로,
그 전까지 커버 없는 글은 목록에서 그림 자리가 빈다.
동기화 한 번이면 풀리고, 그 뒤로는 읽을 때마다 본문을 뒤지지 않는다.

`sameContent` 가 `cover_image` 를 보므로 그 동기화에서 글이 한 번씩 다시 쓰인다.
`updated_at` 이 그때 움직인다 — 내용이 실제로 바뀐 것은 아니지만,
저장된 값이 바뀐 것은 맞다.
