# ADR-0053: 내려간 글은 데우지 말고 확인한다

- 상태: 채택
- 날짜: 2026-09-06
- 관련: ADR-0048(동기화 뒤 캐시 데우기), ADR-0045(캐시 가능한 읽기)

## 배경

노션에서 발행 체크를 풀고 동기화했는데, 그 글이 **두 시간 동안 200 으로 열려 있었다.**

```
HTTP/1.1 200 OK
Age: 7200
X-Vercel-Cache: STALE
```

DB 는 이미 `status: draft` 였다. 목록도 사이트맵도 RSS 도 정확히 그 글을 빼고 있었다.
화면 하나만 옛 모습으로 남아 있었던 것이다.

두 번 요청하니 404 가 됐다. 낡은 캐시가 요청을 받아 재생성을 시작하고,
그다음 요청부터 새 화면이 나가는 stale-while-revalidate 의 정상 동작이다.
문제는 **그 두 번째 요청이 두 시간 동안 오지 않았다**는 것이다.

## 원인

`Age: 7200` 이 가리키는 것은 그 캐시가 **두 시간 전에 만들어졌다**는 사실이다.
두 시간 전은 동기화를 돌린 시각이다. 캐시를 버린 바로 그 요청이,
같은 요청 안에서 옛 화면을 받아 새 캐시로 앉힌 셈이다.

ADR-0048 에서 넣은 데우기가 이렇게 생겼다.

```ts
for (const path of paths) revalidatePath(path);
await warm(paths); // 곧바로 한 번
```

`revalidatePath` 는 "낡음"으로 표시할 뿐이고, 그 표시가 도는 데 시간이 든다.
표시가 아직 닿지 않은 사이에 데우기가 들어가면 **옛 화면을 받아 그것을 새것으로 굳힌다.**
데우기가 문제를 고치는 대신 문제를 연장한 것이다.

정확히 이 경로였는지는 로그로 확정하지 못했다. 다만 `Age` 가 동기화 시각을 가리키는 것,
그리고 데우기가 버림과 같은 시점에 붙어 있다는 것 - 이 둘을 함께 설명하는 이야기는 이것뿐이다.

## 결정

**데우기를 두 번 돌린다.**

```ts
await Promise.allSettled(paths.map(hit));
await sleep(1500);
await Promise.allSettled(paths.map(hit));
```

첫 번째가 재생성을 시작시키고, 두 번째가 새 화면을 받아 앉힌다.
첫 번째가 무엇을 받았는지는 상관하지 않는다 - 그 일의 목적은 재생성을 켜는 것이다.

**닫혀야 할 주소는 확인한다.** 지운 글과 발행을 내린 글의 주소를 실제로 눌러 보고,
404 가 아니면 다시 본다. 세 번까지 보고도 열려 있으면 응답을 실패로 돌린다.

데우기는 실패해도 넘어간다. 못 데우면 첫 방문자가 재생성을 시작할 뿐 잘못된 화면은 아니다.
**닫힘은 다르다.** 초안이 공개로 남는 것은 화면이 조금 낡은 것과 같은 종류의 문제가 아니다.

**발행을 내린 글을 `unpublished` 로 따로 센다.** 예전에는 `synced` 에 섞여 들어가서,
응답만 보고는 "글이 반영됐다"와 "글이 내려갔다"를 구분할 수 없었다.
둘은 확인해야 할 것이 반대다 - 하나는 새 화면이 나오는지, 하나는 주소가 닫혔는지.

## 대가

동기화가 길어진다. 데우기 한 번이 두 번이 되고, 사이에 1.5초를 쉬고,
내려간 글이 있으면 확인에 최대 4초를 더 쓴다.
상한은 300초이고 이미지 이관이 대부분을 차지하므로 여유는 충분하다.

발행 버튼을 누른 사람이 몇 초 더 기다린다. 그 대가로 **누른 순간에 끝난다** -
"발행했는데 안 보인다"도, "내렸는데 아직 열린다"도 남기지 않는다.

## 하지 않은 것

**글 화면의 안전망 주기를 줄이지 않았다.** 1시간을 5분으로 당기면 창이 좁아질 뿐 닫히지는 않는다.
5분이든 1시간이든 "그동안은 초안이 열려 있다"는 사실은 같다. 시간으로 푸는 문제가 아니다.

**`dynamicParams` 를 끄지 않았다.** 빌드 때 목록을 못 박으면 이 문제는 사라지지만,
새 글을 올릴 때마다 배포해야 한다. 노션에서 버튼 하나로 발행한다는 전제가 무너진다.
